# Debug: Re-injected image blip lost at save

## Symptoms

- **Expected**: An image re-injected by the Scribe plugin (Test MD Insert/Replace, real-flow LLM path too) should persist into the saved .docx with a valid `<a:blip r:embed="rIdN"/>` pointing at a `word/media/imageN.png`, so it renders after save + reopen.
- **Actual**: The injected image renders correctly LIVE (in-session) but is LOST at save. The saved docx's injected `<w:drawing>` has a CORRUPT `<pic:blipFill>` with **no `<a:blip>`** — instead `<pic:blipFill dpi="7602275"><a:tile algn="b" sx="41746925" sy="8" tx="67895296" ty="89"/></pic:blipFill>` (garbage numeric fields) and an empty `<pic:spPr>`. On reopen in OO the injected image is BLANK (only its surrounding text survives). The ORIGINAL image in the same doc serializes correctly (`<a:blip r:embed="rId9"/>` → word/media/image1.png).
- **Errors**: No console error; the corruption is silent (renders live, garbage at serialize).
- **Timeline**: Introduced by the Phase 28-01 injection approach (getLocalImagePath + Api.FromJSON + AddDrawing in one callCommand). The 28-02 `ret.url` change fixed LIVE render (was blank-until-reload with ret.path) but did NOT fix save. Contradicts the memory note claiming "ret.url resolves at render AND maps back at save."

## Hypothesis (initial)

`ret.url` (media-id) resolves at RENDER (getFullImageSrc2 / g_oDocumentUrls path→url map) but NOT at SAVE: the CBlipFill rebuilt by FromJSON has a RasterImageId that isn't backed by a registered document media relationship (rId→word/media) at WriteBlipFill time, so the serializer emits tile/dpi garbage instead of `<a:blip>`. Tension: a base64 data-URL rasterImageId SAVES (OO embeds a new media part) but is blank-until-reload live; a media-id (ret.url) renders live but doesn't save. A correct fix likely needs BOTH: render-time resolution AND a registered save relationship for the injected media. word/media/image1.png IS already present — only the blip pointing at it is missing/corrupt.
